# 파라메트릭 서치 (이분탐색으로 최적화 문제 풀기)

## 1. 파라메트릭 서치란?

"최댓값을 최소화하라", "최솟값을 최대화하라" 같은 **최적화 문제**를,

> X가 가능한가? (yes / no)

라는 **결정 문제**로 바꾼 뒤 이분탐색으로 답을 찾는 기법이다.

값 하나를 딱 계산해내는 것이 아니라, "이 값으로 가능한가?"를 반복해서 물어보며 가능/불가능의 경계를 좁혀나간다.

## 2. 언제 사용하는가?

다음 조건을 모두 만족하면 파라메트릭 서치를 의심한다.

- 답이 될 수 있는 값들이 **정렬된 구간**(정수 범위 등)을 이룬다.
- "값 X로 가능한가?"라는 질문에 **단조성**이 있다. 즉 X가 커질수록(또는 작아질수록) 가능 → 불가능(또는 그 반대)으로 **한 번만** 바뀐다.
- "X로 가능한가?"를 판별하는 함수를 답 하나당 O(n) 또는 O(n log n) 정도로 계산할 수 있다.

전형적인 키워드: "최댓값을 최소로", "최솟값을 최대로", "~ 이상/이하로 할 수 있는 최대/최소값".

핵심 판단 기준

> 정답 후보를 하나 고정했을 때, "이 값으로 조건을 만족시킬 수 있는가?"를 빠르게 판별할 수 있고, 그 판별 결과가 후보값 순서대로 단조롭게 바뀌는가?

## 3. 일반 이분탐색과의 차이

| 구분      | 일반 이분탐색 (값 탐색)      | 파라메트릭 서치 (경계 탐색)                  |
| --------- | ---------------------------- | -------------------------------------------- |
| 목적      | 정렬된 배열에서 특정 값 찾기 | 조건을 만족/불만족하는 경계값 찾기           |
| 판별      | `arr[mid] === target`        | `check(mid)` → true / false                  |
| 찾는 대상 | 배열의 인덱스/값             | 답이 될 수 있는 정수(또는 실수) 값 자체      |
| 종료 시점 | 값을 찾거나 못 찾으면 종료   | 가능/불가능의 경계에 `lo === hi`가 되면 종료 |

즉 배열 탐색용 이분탐색이 "이 값이 배열에 있는가"를 묻는다면, 파라메트릭 서치는 "이 값이 조건을 만족하는 가장 작은/큰 값인가"를 묻는다.

## 4. 핵심 절차 4단계

1. 답이 될 수 있는 값의 범위 `[lo, hi]`를 정한다.
2. 판별 함수 `check(x)` : "x로 조건을 만족시킬 수 있는가?"를 정의한다.
3. `check(x)`가 x에 대해 **단조성**을 가지는지 확인한다.
4. 단조성의 패턴과 구하려는 값(최소/최대)에 맞는 이분탐색 템플릿으로 경계를 찾는다.

이 문서는 3번(결정 함수로 바꾸는 법)과 4번(조건문을 정확히 고르는 법)을 집중적으로 다룬다.

## 5. 최적화 문제 → 결정 문제로 바꾸기

최적화 문제를 그대로 풀려고 하면 "어떤 값이 최적인가"를 직접 계산해야 해서 어렵다. 대신 값을 하나 **가정**하고, 그 가정이 **성립하는지만** 판별하면 문제가 훨씬 쉬워지는 경우가 많다.

### 변환 공식

> "조건을 만족하는 X의 최댓값(또는 최솟값)은?"
> ↓
> `check(X)` = "X일 때 조건을 만족할 수 있는가?" (true/false)
> ↓
> `check(X)`가 true인 X 중 최댓값(또는 false인 X 중 최솟값 - 1) 찾기

### 예시: 나무 자르기 (백준 2805)

- 원래 질문: "필요한 나무 길이 M을 채우면서 자를 수 있는 절단기 높이의 **최댓값**은?"
- 그대로 풀면: "높이를 얼마로 해야 하는가?"를 직접 역산해야 해서 어렵다.
- 결정 문제로 변환: `check(H)` = "높이 H로 자르면 `sum(max(0, height - H))`가 M 이상인가?"
- 이제 `check(H)`가 true인 H 중 **가장 큰 값**을 이분탐색으로 찾으면 된다.

이렇게 "정답이 얼마인가"를 직접 구하는 대신 "이 값이 답이 될 자격이 있는가"만 판별하는 함수로 바꾸는 것이 핵심이다.

## 6. 단조성 확인하기

`check(x)`를 x가 작은 값부터 큰 값까지 순서대로 나열했을 때, 결과가 **정확히 한 번만** 바뀌어야 이분탐색이 가능하다.

```
패턴 A:  F F F F ... F T T T T ... T   (x가 커질수록 만족하기 쉬워짐)
패턴 B:  T T T T ... T F F F F ... F   (x가 커질수록 만족하기 어려워짐)
```

`F T F T F` 처럼 여러 번 바뀌면 이분탐색으로 풀 수 없다. 문제를 변형해서 (예: x가 아니라 다른 변수를 기준으로) 다시 단조성을 확인해야 한다.

단조성은 보통 다음과 같은 직관으로 판단한다.

- 자르는 높이가 높아질수록 → 얻는 나무 양은 **줄어든다** (패턴 B, 감소)
- 공유기 사이 최소 거리를 넓게 잡을수록 → 설치 가능한 공유기 수는 **줄어든다** (패턴 B, 감소)
- 그룹 하나가 감당할 수 있는 최대값(용량)을 늘릴수록 → 필요한 그룹 수는 **줄어든다** (패턴 B, 감소)

대부분의 파라메트릭 서치 문제는 "제약을 풀어줄수록(x 증가) 하기 쉬워진다 / 어려워진다"의 직관으로 패턴을 바로 알 수 있다.

## 7. 이분탐색 템플릿을 결정론적으로 고르는 법

여기가 실수가 가장 많이 나는 부분이다. `while (left < right)`를 쓸지 `left <= right`를 쓸지, `left = mid + 1`을 쓸지 `left = mid`를 쓸지는 **감으로 정하는 것이 아니라 아래 규칙으로 기계적으로 결정**할 수 있다.

### 7.1 규칙을 정하는 두 가지 질문

**질문 1. `check(x)`의 패턴은 A(F...FT...T)인가, B(T...TF...F)인가?**

**질문 2. 내가 찾는 값은 "만족하는 것 중 최솟값"인가, "만족하는 것 중 최댓값"인가?**

이 두 질문에 대한 답이 실전에서는 거의 항상 다음 두 조합 중 하나로 떨어진다.

| 조합 | check 패턴     | 찾는 값                   | 템플릿 |
| ---- | -------------- | ------------------------- | ------ |
| ①    | A (F...FT...T) | 만족하는 것 중 **최솟값** | Case A |
| ②    | B (T...TF...F) | 만족하는 것 중 **최댓값** | Case B |

(반대 조합, 즉 "만족하지 않는 것의 경계"를 구하고 싶을 때는 `!check(x)`를 기준으로 다시 위 표에 대입하면 된다. 사실상 독립적인 템플릿은 이 두 개뿐이다.)

### 7.2 Case A: 만족하는 것 중 최솟값 찾기

```
F F F ... F | T T T T ... T
             ↑
           이 경계(첫 T)를 찾는다
```

`mid`가 조건을 만족(`true`)하면 `mid`도 답의 **후보로 남겨야** 하므로 `hi = mid`로 좁힌다.
`mid`가 조건을 만족하지 않으면(`false`) `mid`는 답이 될 수 없으므로 완전히 버리고 `lo = mid + 1`로 좁힌다.

```javascript
function findMinSatisfying(lo, hi, check) {
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2); // 내림(lower mid)
    if (check(mid)) {
      hi = mid; // mid가 답일 수 있으므로 후보로 유지
    } else {
      lo = mid + 1; // mid는 답이 될 수 없으므로 버림
    }
  }
  return lo; // lo === hi, 조건을 만족하는 최솟값
}
```

### 7.3 Case B: 만족하는 것 중 최댓값 찾기

```
T T T ... T | F F F F ... F
             ↑
    이 경계 직전(마지막 T)을 찾는다
```

`mid`가 조건을 만족(`true`)하면 `mid`도 답의 **후보로 남겨야** 하므로 `lo = mid`로 좁힌다.
`mid`가 조건을 만족하지 않으면(`false`) `mid`는 답이 될 수 없으므로 완전히 버리고 `hi = mid - 1`로 좁힌다.

```javascript
function findMaxSatisfying(lo, hi, check) {
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2); // 올림(upper mid) — 반드시 올림!
    if (check(mid)) {
      lo = mid; // mid가 답일 수 있으므로 후보로 유지
    } else {
      hi = mid - 1; // mid는 답이 될 수 없으므로 버림
    }
  }
  return lo; // lo === hi, 조건을 만족하는 최댓값
}
```

### 7.4 내림은 `Math.floor`, `Math.trunc`가 아니다

`lo`, `hi`가 항상 0 이상(배열 인덱스, 양의 정수 답 등)이라면 `Math.floor`와 `Math.trunc`의 결과는 같다. 하지만 답의 범위에 **음수가 포함될 수 있는 문제**(온도, 좌표 차이 등을 다루는 경우)라면 반드시 `Math.floor`를 써야 한다.

```javascript
// lo = -5, hi = -4 인 상황, (lo + hi) / 2 === -4.5

Math.floor(-4.5); // -5  → mid === lo,  lo <= mid < hi 성립 (O)
Math.trunc(-4.5); // -4  → mid === hi,  mid < hi 깨짐      (X)
```

7.2의 `hi = mid` / `lo = mid + 1` 템플릿은 "`lo < hi`이면 항상 `lo <= mid < hi`"라는 불변식에 의존한다. `Math.trunc`는 0 방향으로 반올림하기 때문에 음수 구간에서 `mid`가 `hi`와 같아지는 경우가 생기고, 이때 `check(mid)`가 false면 `lo = mid + 1 = hi + 1`이 되어 `lo`가 `hi`를 넘어버려 불변식이 깨진다. `Math.floor`는 부호와 무관하게 항상 음의 무한대 방향으로 내림하므로 이 불변식을 보장한다.

헷갈릴 여지를 없애려면 답의 범위가 양수뿐이더라도 습관적으로 `Math.floor`를 쓰는 것이 안전하다.

### 7.5 왜 mid를 내림/올림으로 다르게 계산해야 하는가

`lo`와 `hi`를 좁히는 두 가지 방식이 있다.

- **mid를 버리는 갱신** (`lo = mid + 1`, `hi = mid - 1`) : `+1`/`-1`이 항상 범위를 줄여주므로 mid를 내림으로 계산하든 올림으로 계산하든 무한루프가 생기지 않는다.
- **mid를 후보로 남기는 갱신** (`lo = mid`, `hi = mid`) : mid 자체가 그대로 경계에 대입되므로, `lo === hi - 1`인 상황에서 mid 계산 방향을 잘못 고르면 `lo`(또는 `hi`)가 **전혀 줄어들지 않아 무한루프**에 빠진다.

정리하면 다음 규칙 하나로 항상 옳은 선택을 할 수 있다.

> **`lo = mid`로 갱신한다면 → mid는 반드시 올림(`ceil`)으로 계산한다.**
> **`hi = mid`로 갱신한다면 → mid는 내림(`floor`, 기본값)으로 계산해도 안전하다.**

왜 그런지 `lo === hi - 1`인 극단적인 경우로 검증해보면 명확하다.

```javascript
// lo = 4, hi = 5 인 상황

// 내림 mid를 쓰면
Math.floor((4 + 5) / 2); // = 4  → mid는 lo와 같다

// 만약 이때 lo = mid로 갱신한다면
// lo = 4 (변화 없음!) → 무한루프

// 올림 mid를 쓰면
Math.ceil((4 + 5) / 2); // = 5  → mid는 hi와 같다

// 이때 lo = mid로 갱신하면
// lo = 5 → 진행됨 (lo === hi가 되어 루프 종료)
```

반대로 `hi = mid`로 갱신하는 Case A에서 올림 mid를 쓰면 `hi`가 줄어들지 않아 같은 문제가 생긴다. 실제로 실행해서 확인한 결과다.

```javascript
// 잘못된 예: Case B인데 내림 mid + lo = mid를 사용
function wrong(lo, hi, check) {
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2); // BUG: 올림이어야 함
    if (check(mid)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
// lo=4, hi=5 근처에서 무한루프 발생 확인됨
```

### 7.6 무한루프 디버깅 체크리스트

이분탐색이 멈추지 않는다면 순서대로 확인한다.

1. `while` 조건이 `lo < hi`인가, `lo <= hi`인가? 경계 탐색 템플릿(7.2, 7.3)은 `lo < hi`를 쓴다.
2. `lo = mid`로 갱신하면서 mid를 **내림**으로 계산하고 있지 않은가? → 올림으로 바꾼다.
3. `hi = mid`로 갱신하면서 mid를 **올림**으로 계산하고 있지 않은가? → 내림으로 바꾼다.
4. 내림을 `Math.trunc`로 쓰고 있는데 `lo`, `hi`에 음수가 포함되지 않는가? → `Math.floor`로 바꾼다.
5. `lo`, `hi`의 초기값이 실제 답을 포함하는 범위인가? (답이 초기 범위 밖에 있으면 영원히 못 찾는다)
6. `check` 함수가 정말 단조성을 만족하는가? (F T F 처럼 여러 번 바뀌면 애초에 이분탐색 대상이 아니다)

### 7.7 참고: `left = mid + 1` / `right = mid - 1` 형태와의 관계

가끔 `left = mid`, `right = mid` 대신 아래처럼 mid를 항상 버리는 이분탐색 코드를 보게 된다.

```javascript
function search(arr, target) {
  let left = 0, right = arr.length - 1;
  while (left <= right) {
    const mid = Math.floor((left + right) / 2);
    if (arr[mid] === target) return mid; // 일치하면 즉시 종료
    else if (arr[mid] < target) left = mid + 1;
    else right = mid - 1;
  }
  return -1; // 못 찾음
}
```

이건 정렬된 배열에서 **정확히 일치하는 값**을 찾는 일반 이분탐색이다. "일치"라는 세 번째 경우가 있어서 찾으면 그 자리에서 바로 `return`해버리므로, 나머지 두 분기(`<`, `>`)는 mid를 후보로 남길 필요 없이 **항상 버려도** 안전하다.

파라메트릭 서치의 `check(x)`는 true/false 두 갈래뿐이라 이런 즉시 종료 조건이 없다. 그래서 이 형태를 그대로 가져오려면, mid가 조건을 만족했을 때 그 값을 잃어버리지 않도록 **별도의 `answer` 변수에 기록**해야 한다. 이게 바로 8번에서 다루는 패턴이다.

세 가지 형태를 정리하면 다음과 같다.

| 형태                              | 용도                                | while 조건    | mid 처리                                                          |
| --------------------------------- | ----------------------------------- | -------------- | ------------------------------------------------------------------ |
| 정확히 일치하는 값 찾기           | 정렬된 배열에서 target 검색         | `left <= right` | 일치하면 즉시 반환, 아니면 무조건 버림 (`left=mid+1`/`right=mid-1`) |
| `answer` 변수 패턴 (8번)          | 결정 문제, 초보자용 안전한 방식     | `lo <= hi`      | 만족하면 `answer`에 기록 후 계속 버림, 불만족이면 버림              |
| 경계 직접 좁히기 (7.2 · 7.3)      | 결정 문제, 더 타이트한 방식         | `lo < hi`       | 만족하면 후보로 남김(`lo=mid`/`hi=mid`), 불만족이면 버림            |

셋 다 "이분탐색으로 절반씩 줄여나간다"는 원리는 같고, **mid를 판단한 뒤 후보로 남길지(경계에 그대로 대입) 완전히 버릴지(`±1`)** 의 차이일 뿐이다. mid를 완전히 버리는 형태는 항상 `Math.floor`만 쓰면 되므로 반올림 방향을 고민할 필요가 없다는 것이 가장 큰 장점이다.

## 8. 더 안전한 대안: `answer` 변수 패턴

mid 반올림 규칙이 헷갈린다면, mid를 후보로 "남기지" 않고 항상 **버리는 방식**으로만 좁히면서 별도의 `answer` 변수에 최선의 값을 기록하는 패턴을 쓸 수도 있다. 이 패턴은 `lo <= hi`, `mid = floor`만 사용하므로 무한루프 걱정이 없다.

```javascript
// 최댓값 찾기 버전 (Case B와 동일한 문제를 푸는 대안)
function findMaxSatisfyingSafe(lo, hi, check) {
  let answer = lo - 1; // 못 찾았을 때를 대비한 초기값
  while (lo <= hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (check(mid)) {
      answer = mid; // 일단 후보로 기록
      lo = mid + 1; // 더 큰 값도 가능한지 계속 탐색
    } else {
      hi = mid - 1;
    }
  }
  return answer;
}

// 최솟값 찾기 버전
function findMinSatisfyingSafe(lo, hi, check) {
  let answer = hi + 1;
  while (lo <= hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (check(mid)) {
      answer = mid;
      hi = mid - 1; // 더 작은 값도 가능한지 계속 탐색
    } else {
      lo = mid + 1;
    }
  }
  return answer;
}
```

- 장점: mid 계산이 항상 `floor` 하나뿐이라 실수할 여지가 적다.
- 단점: `lo === hi`로 끝나는 7.2/7.3 템플릿보다 코드가 한 줄 더 필요하고, "답을 못 찾는 경우"를 직접 처리해야 한다.

**추천**: 처음에는 8번의 `answer` 패턴으로 안전하게 작성하고, 템플릿에 익숙해지면 7.2/7.3의 `lo === hi` 패턴으로 넘어가는 것을 권장한다.

## 9. 실전 예제

### 9.1 나무 자르기 (Case B — 최댓값 찾기)

톱의 높이 H로 나무를 자를 때 얻는 나무 길이가 `M` 이상이 되도록 하는 **최대** H를 구한다.

```javascript
function check(H, trees, M) {
  let sum = 0;
  for (const height of trees) {
    if (height > H) sum += height - H;
  }
  return sum >= M; // H가 낮을수록(=자르는 양이 많을수록) 만족하기 쉬움 → 패턴 B
}

function solve(trees, M) {
  let lo = 0;
  let hi = Math.max(...trees);
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2); // Case B → 올림
    if (check(mid, trees, M)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
```

- `check`는 H가 작을수록(제약이 느슨할수록) true → 패턴 B(T...TF...F)
- "최댓값"을 구하므로 → `lo = mid` 갱신 → mid는 **올림**

### 9.2 공유기 설치 (Case B — 최댓값 찾기)

집 좌표들 중 C개의 공유기를 설치할 때, 인접한 두 공유기 사이 거리의 **최솟값을 최대화**한다.

```javascript
function check(gap, houses, C) {
  let count = 1;
  let last = houses[0];
  for (let i = 1; i < houses.length; i++) {
    if (houses[i] - last >= gap) {
      count++;
      last = houses[i];
    }
  }
  return count >= C; // gap이 좁을수록 더 많이 설치 가능 → 패턴 B
}

function solve(houses, C) {
  houses.sort((a, b) => a - b);
  let lo = 1;
  let hi = houses[houses.length - 1] - houses[0];
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2); // Case B → 올림
    if (check(mid, houses, C)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
```

- "설치 가능한 공유기 수가 C개 이상인가"는 gap이 작을수록 만족하기 쉬움 → 패턴 B
- "최솟값을 최대화"이므로 gap의 **최댓값**을 구함 → `lo = mid`, mid는 올림

### 9.3 배열 나누기 (Case A — 최솟값 찾기)

배열을 순서를 유지한 채 K개의 연속 구간으로 나눌 때, 각 구간 합의 **최댓값을 최소화**한다.

```javascript
function check(limit, arr, K) {
  let groups = 1;
  let sum = 0;
  for (const v of arr) {
    if (sum + v > limit) {
      groups++;
      sum = 0;
    }
    sum += v;
  }
  return groups <= K; // limit이 클수록 그룹 수가 줄어 만족하기 쉬움 → 패턴 A
}

function solve(arr, K) {
  let lo = Math.max(...arr); // 각 구간은 원소 하나보다 작을 수 없음
  let hi = arr.reduce((a, b) => a + b, 0);
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2); // Case A → 내림
    if (check(mid, arr, K)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}
```

- "그룹 수가 K 이하인가"는 limit이 클수록 만족하기 쉬움 (limit 증가 → F...FT...T) → 패턴 A
- "최댓값을 최소화"이므로 limit의 **최솟값**을 구함 → `hi = mid`, mid는 내림(기본값)

## 10. 최종 체크리스트

새 문제를 파라메트릭 서치로 풀 때 이 순서를 그대로 따라가면 조건문을 감으로 정할 필요가 없다.

1. 답 후보의 범위 `[lo, hi]`를 정한다.
2. `check(x)`를 정의한다: "x로 조건을 만족시킬 수 있는가?"
3. x가 커질 때 `check(x)`가 `F→T`(패턴 A)인지 `T→F`(패턴 B)인지 확인한다.
4. 구하려는 값이 "만족하는 것 중 최솟값"인지 "최댓값"인지 정한다.
5. 아래 표에서 조합에 맞는 템플릿을 그대로 가져다 쓴다.

| 패턴           | 구하는 값 | 갱신                            | mid 방향   |
| -------------- | --------- | ------------------------------- | ---------- |
| A (F...FT...T) | 최솟값    | `if(true) hi=mid else lo=mid+1` | 내림(기본) |
| B (T...TF...F) | 최댓값    | `if(true) lo=mid else hi=mid-1` | **올림**   |

한 줄 요약: **mid를 후보로 남기며 갱신(`lo=mid`)할 때만 올림으로 계산한다. 나머지는 전부 내림이면 된다.**
