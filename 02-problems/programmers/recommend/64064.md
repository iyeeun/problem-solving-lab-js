# [불량 사용자](https://school.programmers.co.kr/learn/courses/30/lessons/64064)

## 문제 요약

- 개인정보 보호를 위해 일부 문자가 '*'로 마스킹된 제재 아이디(banned_id) 목록이 주어짐
- 실제 사용자 아이디(user_id) 목록 중 제재 아이디와 매칭되는 조합을 찾아, 가능한 제재 아이디 집합의 개수를 구함
- 같은 사용자 집합이면 순서가 달라도 같은 것으로 취급

## 입력 구조

- user_id 배열 크기: 1 이상 8 이하
- user_id 각 원소 길이: 1 이상 8 이하 (소문자, 숫자로만 구성)
- user_id 는 중복 없음
- banned_id 배열 크기: 1 이상 user_id 배열 크기 이하
- banned_id 각 원소 길이: 1 이상 8 이하 (소문자, 숫자, '*' 로 구성)
- banned_id 각 원소는 '*' 를 하나 이상 포함
- 매칭은 대소문자를 구분하며, 결과 집합에서 순서는 상관없음

## 문제 유형 분류

- 완전탐색 / 백트래킹 / DFS

## 사고 과정

### 1. 왜 이 유형인가

- banned_id 하나마다 매칭 가능한 user_id 후보가 여러 명일 수 있고, 그 후보들이 다른 banned_id의 후보와 겹치기도 해서 "각 banned_id에 서로 다른 사용자를 하나씩 배정하는 모든 경우"를 직접 찾아봐야 함
- user_id, banned_id 배열 크기가 모두 8 이하로 매우 작아서 완전탐색(백트래킹)으로 모든 배정을 시도해도 충분히 감당 가능
- 최종적으로 구해야 하는 건 순서 없는 "사용자 집합"의 개수이므로, 배정 순서만 다른 결과는 하나로 묶어 세는 중복 제거가 필요함

### 2. 왜 다른 접근은 안되는가

- 그리디: banned_id마다 후보가 여러 명이라 어떤 사용자를 먼저 배정할지 정할 기준이 없고, 한 배정이 다른 banned_id의 배정 가능 여부에 영향을 주므로 그리디로 확정할 수 없음
- 후보 집합끼리 단순 집합 연산: 후보 사용자가 여러 banned_id에 걸쳐 겹치므로, 실제로 한 사용자가 한 banned_id에만 쓰이는 유효한 조합인지는 배정을 직접 만들어봐야 확인 가능

## 문제 풀이

- [64064.js](./64064.js)

```
1. possible[b]: banned_id[b]와 길이가 같고 '*'가 아닌 위치의 문자가 모두 일치하는 user_id들을 모아 미리 계산
2. dfs(cur_group, path)로 banned_id를 앞에서부터 하나씩 순회하며, possible[cur_group] 중 아직 안 쓴 사용자를 골라 path에 추가
3. visited로 이미 다른 banned_id에 배정된 사용자는 건너뛰고, 배정 후에는 visited 해제(백트래킹)로 다른 조합도 계속 탐색
4. 모든 banned_id에 배정이 끝나면(cur_group === banned_id.length) path를 정렬해 문자열로 만들고 Set에 저장해 순서만 다른 중복 조합을 제거
5. 최종 Set의 크기가 가능한 사용자 집합의 개수
```

## 해결 전략

### 알고리즘 선택 이유

- 각 banned_id에 사용자를 하나씩 배정하되 이미 쓰인 사용자는 제외해야 하는 제약 충족 문제라, 배정을 하나씩 시도하고 막히면 되돌리는 백트래킹이 자연스럽게 들어맞음
- 배정 순서가 달라도 같은 사용자 집합이면 같은 결과이므로, dfs로 나온 모든 경로를 정렬 후 문자열로 정규화해 Set에 담아 중복을 걸러냄

### 자료구조 선택 이유

- possible 배열: banned_id별로 매칭되는 user_id 후보를 미리 걸러둬서, dfs 안에서 매번 전체 user_id를 다시 검사하지 않도록 함
- Map(visited): 어떤 user_id가 이미 다른 banned_id에 배정됐는지 빠르게 확인하고, 백트래킹 시 다시 false로 되돌리기 위해 사용
- Set(result): path.sort()로 정규화한 문자열을 키로 써서 순서만 다른 동일 조합을 자동으로 하나로 합침

## 시간/공간 복잡도

- user_id 개수를 n, banned_id 개수를 b, 문자열 길이를 L이라 하면
- 시간: possible 계산에 O(b \* n \* L), dfs는 최악의 경우 서로 다른 사용자를 순서대로 배정하는 경우의 수인 O(n! / (n-b)!)만큼 분기하므로 전체는 이 두 부분의 합
- 공간: possible과 visited에 O(n + b), dfs 재귀 깊이와 path에 O(b), result에는 최대 가능한 조합 개수만큼 저장

## JS 구현 포인트

- Array.from({ length: banned_id.length }, () => new Array())로 possible을 만들어, banned_id마다 독립된 배열을 갖도록 함(new Array(n).fill([])처럼 같은 배열 참조를 공유하는 실수를 피함)
- path.sort()로 정렬한 배열을 JSON.stringify로 문자열화해 Set의 키로 사용, 배열은 참조가 달라 그대로는 Set에서 중복 판정이 안 되는 점을 문자열 변환으로 해결
- visited.set(b, true) 후 재귀 호출하고 돌아와서 다시 false로 되돌리는 전형적인 백트래킹 패턴으로 사용한 사용자를 다음 배정 시도에서 제외
