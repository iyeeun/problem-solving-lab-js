# [[1차] 추석 트래픽](https://school.programmers.co.kr/learn/courses/30/lessons/17676)

## 문제 요약

- 응답 완료 시각과 처리 시간이 기록된 로그를 분석해 임의의 1초 구간에 처리되는 요청의 최대 개수를 구함
- 요청의 시작 시각과 끝 시각을 모두 처리 시간에 포함함

## 입력 구조

- lines: 응답 완료 시각과 처리 시간이 담긴 로그 문자열 배열
- lines의 길이 N: 1 이상 2000 이하
- 응답 완료 시각: `2016-09-15 hh:mm:ss.sss` 형식이며 오름차순으로 정렬되어 있음
- 처리 시간: 0.001초 이상 3.000초 이하이며 최대 소수점 셋째 자리까지 주어짐
- 초당 최대 처리량을 정수로 반환

## 문제 유형 분류

- 완전탐색
- 구간 겹침
- 시뮬레이션

## 사고 과정

### 1. 왜 이 유형인가

- 각 요청은 처리 시작 시각과 종료 시각을 양 끝으로 하는 닫힌 구간으로 볼 수 있음
- 초당 최대 처리량은 임의의 1초 구간과 조금이라도 겹치는 요청 구간의 최대 개수임
- 최대 처리량을 만드는 1초 구간의 시작점을 모든 밀리초마다 검사할 필요는 없음
- 최대 처리량을 만드는 임의의 1초 구간을 오른쪽으로 옮겨, 포함된 요청 중 가장 이른 종료 시각에 시작점을 맞춰도 기존 요청 수가 줄지 않음
  - 가장 이른 종료 시각의 요청은 새 구간의 시작점에서 여전히 겹침
  - 나머지 요청은 그 시각 이후에 종료되므로 새 구간의 왼쪽으로 빠지지 않음
  - 구간의 끝도 오른쪽으로 이동하므로 기존 요청이 오른쪽으로 빠지지 않음
- 따라서 각 요청의 종료 시각 `E`를 기준으로 `[E, E + 999ms]`를 검사하면 최대 처리량을 찾을 수 있음
- 입력이 종료 시각 오름차순으로 정렬되어 있으므로 기준 요청보다 앞에서 종료된 요청은 검사 구간과 겹치지 않음
- 기준 요청 이후의 요청은 종료 시각이 `E` 이상임이 보장되므로, 해당 요청의 시작 시각이 `E + 999ms` 이하인지만 확인하면 겹침을 판단할 수 있음

### 2. 왜 다른 접근은 안되는가

- 하루의 모든 밀리초를 1초 구간의 시작점으로 두고 검사하면 답은 구할 수 있지만 불필요한 후보를 많이 확인하게 됨
- 다른 요청의 시작 시각이 1초 구간 내부에 있는지만 보면, 구간보다 먼저 시작해서 구간 도중까지 처리 중인 요청을 놓칠 수 있음
- 일반적인 두 닫힌 구간 `[A, B]`, `[C, D]`는 `A <= D`이고 `B >= C`일 때 겹침
- 이 풀이에서는 종료 시각순 정렬과 뒤쪽 요청만 확인한다는 조건 덕분에 `다른 요청의 종료 시각 >= 기준 종료 시각`이 이미 성립하므로 시작 시각만 비교할 수 있음
- 힙으로 처리 중인 요청을 관리할 수도 있지만 N이 2000 이하이고 O(N^2) 완전탐색으로 충분하므로 별도의 우선순위 큐가 필요하지 않음

## 문제 풀이

- [17676.js (55분 소요)](./17676.js)

```
1. 각 로그에서 응답 완료 시각과 처리 시간을 분리함
2. 모든 로그가 같은 날짜이므로 시, 분, 초, 밀리초를 자정부터 지난 밀리초로 변환해 종료 시각을 구함
3. 처리 구간이 시작과 끝을 모두 포함하므로 종료 시각 - 처리 시간 + 1ms로 시작 시각을 구함
4. 각 요청의 [시작 시각, 종료 시각]을 times에 저장함
5. 각 요청의 종료 시각 E를 1초 측정 구간의 시작점으로 선택하고, 측정 구간을 [E, E + 999ms]로 정함
6. 기준 요청 자신을 처리량에 포함하고, 종료 시각순으로 뒤에 있는 요청들을 확인함
7. 뒤쪽 요청의 시작 시각이 E + 999ms 이하라면 측정 구간과 겹치므로 처리량을 증가시킴
8. 모든 종료 시각에서 구한 처리량 중 최댓값을 반환함
```

## 해결 전략

### 알고리즘 선택 이유

- 모든 로그가 종료 시각순으로 정렬되어 있다는 조건을 이용해 각 종료 시각을 1초 구간의 시작점 후보로 선택함
- 각 후보에서 뒤쪽 로그를 순회하며 겹치는 요청을 직접 세는 완전탐색을 사용함
- N이 최대 2000이므로 최대 약 N^2번 비교하는 방식으로 충분함

### 자료구조 선택 이유

- `times` 배열: 각 요청의 시작 시각과 종료 시각을 `[startTime, endTime]` 쌍으로 저장함
- 입력 순서를 유지해 `times`도 종료 시각 오름차순이 되므로 별도의 정렬이 필요하지 않음
- `processing` 변수: 현재 1초 측정 구간과 겹치는 요청 수를 저장함

## 시간/공간 복잡도

- 로그 수를 N이라 하면
- 시간: 각 종료 시각마다 뒤쪽 로그를 확인하므로 O(N^2)
- 공간: 모든 요청의 시작 시각과 종료 시각을 저장하므로 O(N)

## JS 구현 포인트

- 모든 로그가 같은 날짜에 속하므로 `Date` 객체 없이 시각을 자정부터 지난 밀리초 정수로 변환함
- `split()` 결과인 `h`, `m`, `s`, `ms`는 문자열이므로 단항 `+`를 사용해 숫자로 변환함
- 특히 `endTime`에 `ms`를 더할 때 숫자로 변환하지 않으면 숫자 덧셈이 아니라 문자열 연결이 발생함
- 처리 시간 문자열에서 `s`를 제거한 뒤 1000을 곱해 밀리초로 변환함
- 소수 연산의 오차를 더 명확하게 방지하려면 처리 시간을 밀리초로 바꾼 뒤 `Math.round()`를 적용할 수 있음
- 1초 구간과 처리 구간은 양 끝을 포함하므로 측정 구간의 끝은 `시작 시각 + 999ms`, 요청 시작 시각은 `종료 시각 - 처리 시간 + 1ms`로 계산함
- 현재 풀이가 뒤쪽 요청의 시작 시각만 비교할 수 있는 이유는 입력과 `times`가 종료 시각 오름차순을 유지하기 때문임
