# Problem Solver

이 저장소(Problem Solving Lab - JS)의 코딩 테스트 문제 풀이 흐름을 돕는 스킬이다.
다음 4가지 모드로 동작한다. 사용자의 요청을 보고 어떤 모드인지 판단해서 해당 섹션의 절차를 따른다.

| 모드 | 트리거 예시 | 하는 일 |
|------|-------------|---------|
| **문제 시작** | "이 문제 풀게 <링크>", "문제 시작", "세팅해줘" | 올바른 경로에 `.js`/`.md`/로그 스캐폴딩 |
| **문제 요약** | "요약해줘", "정리해줘", "풀이 정리" | `.md`를 problem-template 형식으로 채움 |
| **힌트** | "힌트 줘", "막혔어", "모르겠어" | 단계적으로 힌트를 조금씩 제공 |
| **로그 작성** | "로그 남겨줘", "오늘 배운 거", "막힌 거 기록", "회고" | 오늘 학습 로그에 배운 점/막힌 점/실수 기록 |

작업 전에 반드시 아래 **공통 규칙**을 먼저 읽는다.

## 공통 규칙

### 저장소 구조

- `02-problems/` — 플랫폼별 문제 풀이
  - `programmers/basic/` — 프로그래머스 **코딩 기초 트레이닝**
  - `programmers/beginner/` — 프로그래머스 **코딩테스트 입문**
  - `programmers/practice/` — 프로그래머스 **고득점 Kit** (현재 진행 중인 로드맵)
  - `boj/` — 백준(acmicpc.net)
- `02-problems/problem-template.md` — 문제 요약 `.md`의 기준 템플릿
- `99-notes/logs/` — 학습 로그
  - `YYYY-MM.md` — 월별 일일 회고 로그
  - `daily-template.md` — 일일 로그 항목 템플릿
  - `programmers-practice.md` — 고득점 Kit 유형별 문제 트래커

### 링크에서 경로/파일명 결정

- **프로그래머스**: URL이 `.../learn/courses/30/lessons/{ID}` 형태이면 파일명은 `{ID}.js`, `{ID}.md`
  - 어느 하위 폴더(basic/beginner/practice)인지는 문제 세트에 따라 결정한다.
  - 판단 방법(우선순위 순):
    1. 사용자가 "고득점 Kit", "입문", "기초 트레이닝" 등 세트를 명시했으면 그대로 따른다.
    2. `99-notes/logs/programmers-practice.md`에 이미 해당 문제가 있으면 `practice`.
    3. 최근 `git log` / 로그 파일상 현재 진행 중인 로드맵을 확인한다. (기본값은 `practice` — 고득점 Kit)
    4. 그래도 애매하면 사용자에게 어느 세트인지 짧게 확인한다.
- **백준**: URL이 `acmicpc.net/problem/{ID}` 형태이면 `boj/{ID}.js`, `boj/{ID}.md`
- 같은 문제의 **다른 풀이**를 추가할 때는 `{ID}_1.js`, `{ID}_2.js` 처럼 접미사를 붙인다 (예: `42884_1.js`).

### 문제 내용 수집

문제 제목·제약조건·입출력 예시가 필요하면 다음 순서로 시도한다.

1. `mcp__workspace__web_fetch` 로 링크를 가져온다.
2. 프로그래머스는 JS 렌더링이라 본문이 안 나올 수 있다. 그 경우 Claude in Chrome MCP로 페이지를 렌더링해 읽는다.
3. 둘 다 안 되면 사용자에게 문제 본문/제약조건을 붙여넣어 달라고 요청한다.

절대 추측으로 제약조건을 지어내지 않는다. 확인되지 않은 값은 사용자에게 묻는다.

### 톤 & 형식 일관성

작업 전 같은 폴더의 기존 `.md`/`.js` 파일을 최소 1개 열어 스타일을 맞춘다.

- `.js`: 2-space 들여쓰기, `function solution(...)` 형태, 헬퍼는 내부 함수로. 기존 파일 스타일을 따른다.
- `.md`: 한국어, 담백한 설명체("~함", "~임" 종결), 불릿 위주. 과장, 군더더기 없이 사실 위주로.
- 커밋은 하지 않는다. 파일만 만들고 사용자가 직접 커밋하도록 둔다(관례: `daily: YYMMDD`).

### 표기 규칙 (중요)

작성하는 모든 파일(.md, 로그 등)에는 **키보드로 바로 입력할 수 있는 문자만** 쓴다. 타이핑할 수 없는 특수 유니코드 기호를 쓰지 않는다.

- 화살표(→, ⇒, ↔) 대신: `->` 또는 한국어로 풀어씀
- 가운데점(·) 대신: 쉼표(,)나 "및", "과/와"
- 부등호+등호(≤, ≥, ≠) 대신: `<=`, `>=`, `!=` 또는 "이상/이하/미만/초과" 한국어
- em/en 대시(—, –) 대신: 하이픈(-)
- 곱셈/나눗셈 기호(×, ÷) 대신: `*`, `/`
- 그 밖에 키보드로 못 치는 기호도 ASCII나 한글로 대체한다.
- 예외: 일일 로그 템플릿의 이모지 소제목(오늘 한 내용/배운 내용/막힌 내용/실수 패턴/링크 앞의 이모지)은 템플릿 고유 요소이므로 그대로 유지한다.

## 파일 형식 레퍼런스

아래는 각 파일의 기준 뼈대다. 세부 문구·스타일은 저장소의 실제 템플릿과 같은 폴더 최신 파일을 기준으로 확인하고, 원본이 바뀌었으면 원본을 따른다(아래는 baseline).

### 풀이 요약 `.md` — `02-problems/problem-template.md` 기준

```markdown
# [문제명](문제링크)

## 문제 요약

- 핵심 요구사항

## 입력 구조

- N, 범위, 제약조건

## 문제 유형 분류

- DP / Greedy / BFS / Two Pointer / ...

## 사고 과정

### 1. 왜 이 유형인가

### 2. 왜 다른 접근은 안되는가

## 문제 풀이

- [ (n분 소요)]()

​```
풀이 간단 설명
​```

## 해결 전략

### 알고리즘 선택 이유

### 자료구조 선택 이유

## 시간/공간 복잡도

- 시간: O()
- 공간: O()

## JS 구현 포인트

- JS로 구현할 때 신경 쓴 포인트
```

- 섹션 순서·제목은 이 구조를 그대로 유지한다.
- **⚠️ 입력 구조의 숫자에는 천 단위 콤마를 절대 쓰지 않는다.** `10000` (O), `10,000` (X). 예: "1 이상 10000 이하", "-30000 이상 30000 이하".
- 유형 분류는 대분류부터 세부 알고리즘까지 나열한다(예: Greedy, 그래프, MST, 크루스칼, Union-Find 순).
- **"문제 풀이" 형식은 풀이 개수에 따라 다르다.**
  - 풀이가 **1개**면 불릿 한 줄 뒤에 코드펜스 블록으로 단계 설명을 둔다.
    - 예: `- [42861.js (7분 소요)](./42861.js)` 아래에 코드펜스로 `1.`, `2.` 단계 설명을 둔다.
  - 풀이가 **여러 개**면 번호 목록으로 각 풀이를 나열하고, 각 항목 아래에 코드펜스 블록으로 그 풀이의 단계 설명을 둔다. **시도한 순서대로** 나열한다.
    - 예: `1. [42884_1.js (39분 소요)](./42884_1.js)` 아래 코드펜스 설명, 이어서 `2. [42884.js (4분 소요)](./42884.js)` 아래 코드펜스 설명.
    - 추가 풀이 파일명은 `{ID}_1.js`, `{ID}_2.js` 접미사를 쓴다.
  - 링크 텍스트에는 항상 `(n분 소요)` 형태로 소요 시간을 포함한다.
- "JS 구현 포인트"·"해결 전략" 등은 담백한 불릿 문장으로 적는다(JS 코드 스니펫은 넣지 않아도 된다).

### 풀이 코드 `.js`

```javascript
function solution(/* 문제 시그니처에 맞는 인자 */) {
  let answer = 0;

  return answer;
}
```

- 2-space 들여쓰기, `function solution(...)` 형태.
- 헬퍼는 `solution` 내부 함수로 선언(예: `find`, `union`).
- 백준이면 `input`을 읽어 파싱하는 입출력 구조에 맞춘 stub.

### 일일 로그 항목 — `99-notes/logs/daily-template.md` 기준

```markdown
### 2026-00-00

#### 📌 오늘 한 내용

-
-

#### 🧠 배운 내용

-
-

#### ❗ 막힌 내용

-
-

#### 🔁 실수 패턴

-

#### 🔗 링크

```

- 월별 파일 `99-notes/logs/{YYYY-MM}.md` 안에 날짜 오름차순으로 이 블록을 추가한다.
- 항목 사이 구분선(`---`)은 그 파일의 기존 관례를 따른다.
- "🔗 링크"는 `- [문제명](/02-problems/.../{ID}.md)` 처럼 저장소 루트 기준 경로로.

### 고득점 Kit 트래커 — `99-notes/logs/programmers-practice.md`

- 유형별 섹션(`### 1. 해시`, `### 6. 탐욕법 (Greedy)` 등) 아래에
  `- [문제명](/02-problems/programmers/practice/{ID}.md)` 한 줄을 추가한다.
- 해당 유형 섹션이 비어 있으면 제목 아래에 첫 항목으로 추가한다.

## 모드 1: 문제 시작

사용자가 문제 링크를 주며 풀이를 시작할 때. 코드 작성 전 파일 골격만 세팅한다.

**절차:**

1. 링크에서 플랫폼·ID·하위 폴더를 결정한다(공통 규칙의 매핑 참고). 애매하면 확인한다.
2. **문제 내용 수집** 규칙으로 제목/제약조건을 확보한다.
3. 최근 `daily`로 시작하는 커밋을 참고해 그날 추가된 파일 세트를 확인한다.
   `git log --oneline | grep daily` 후 `git show <hash> --stat` 로 어떤 파일들이 함께 바뀌는지 본다.
4. 다음 파일을 생성한다.
   - `02-problems/.../{ID}.js` — 풀이 stub:
     ```javascript
     function solution() {
       let answer = 0;

       return answer;
     }
     ```
     (인자는 문제의 시그니처에 맞춘다. 백준이면 입출력 구조에 맞는 stub.)
   - `02-problems/.../{ID}.md` — `problem-template.md`를 복사해 제목/링크와 "문제 요약", "입력 구조" 정도만 채운 빈 템플릿. 나머지 섹션은 비워 둔다(모드 2에서 채움).
5. 로그를 갱신한다.
   - `99-notes/logs/{YYYY-MM}.md` 의 오늘 날짜 항목(`daily-template.md` 형식)에 "오늘 한 내용"과 "🔗 링크"에 해당 문제를 추가한다. 오늘 날짜 항목이 없으면 템플릿을 복사해 새로 만든다.
   - 고득점 Kit(`practice`) 문제면 `99-notes/logs/programmers-practice.md`의 해당 유형 섹션에 `- [문제명](/02-problems/programmers/practice/{ID}.md)` 링크를 추가한다. 유형은 문제 태그로 판단하고 애매하면 확인한다.
6. 만든 파일 경로를 사용자에게 알려주고, 풀이는 사용자가 직접 작성하도록 둔다(먼저 코드를 다 써주지 않는다).

## 모드 2: 문제 요약

풀이를 끝냈거나 진행 중인 문제의 `.md`를 채운다.

**절차:**

1. 대상 문제의 `{ID}.js`(사용자의 실제 풀이)와 `{ID}.md`를 읽는다.
2. `02-problems/problem-template.md`의 섹션 구조를 그대로 따른다.
   순서: 제목/링크, 문제 요약, 입력 구조, 문제 유형 분류, 사고 과정(왜 이 유형인가 / 왜 다른 접근은 안 되는가), 문제 풀이(소요 시간, 코드 링크, 간단 설명), 해결 전략(알고리즘, 자료구조 선택 이유), 시간/공간 복잡도, JS 구현 포인트.
3. 같은 폴더의 잘 작성된 기존 `.md`(예: `programmers/practice/42861.md`)를 레퍼런스로 열어 **동일한 톤과 상세도**로 작성한다.
   - 사용자의 실제 코드에 근거해서 쓴다. 코드에 없는 최적화나 자료구조를 지어내지 않는다.
   - "JS 구현 포인트"에는 정렬 비교함수, 경로 압축, 구조 분해 등 JS 특유의 포인트를 담백한 불릿 문장으로 담는다(코드 스니펫은 넣지 않아도 된다).
   - 복잡도는 실제 코드 기준으로 계산해 근거와 함께 적는다.
4. "문제 풀이"의 소요 시간은 사용자가 알려준 값을 쓰고, 모르면 비워 두거나 물어본다.
5. 필요하면 로그(`{YYYY-MM}.md`의 배운 내용/막힌 내용/실수 패턴, `programmers-practice.md` 링크)도 갱신한다.

**반드시 지킬 것 (파일 형식 레퍼런스 참고):**

- **입력 구조의 숫자에 천 단위 콤마를 쓰지 않는다.** `10000` (O) / `10,000` (X).
- **풀이가 여러 개면** 번호 목록으로 시도한 순서대로 나열하고, 각 풀이마다 코드펜스 블록을 둔다.
- JS 코드 스니펫은 넣지 않아도 된다.

## 모드 3: 힌트

문제를 스스로 풀도록 **단계적으로** 힌트를 준다. 답을 한 번에 주지 않는다.

**핵심 원칙: 고정 단계로, 한 요청에 한 단계씩만.**

기본적으로 1단계부터 시작해 사용자가 힌트를 더 요청할 때마다 다음 단계로 내려간다.
단, 직전 대화 맥락을 읽어 사용자가 이미 어디까지 왔는지 파악하고(이미 유형을 알면 1단계는 건너뛰는 식) 반복을 피한다.

**단계:**

1. **유형/관점** — 어떤 알고리즘 유형·분류로 접근하면 좋을지 방향만. (예: "이건 그리디로 볼 수 있어요. 무엇을 기준으로 정렬할지 생각해보세요.")
2. **핵심 아이디어** — 풀이의 결정적 관찰/성질 하나. 구현은 말하지 않는다.
3. **접근 스케치** — 어떤 자료구조로 어떤 순서로 처리하는지 큰 흐름. 코드는 아직.
4. **의사코드 / 부분 코드** — 핵심 로직의 의사코드나 일부 조각.
5. **전체 풀이** — 사용자가 명시적으로 "답 알려줘"라고 할 때만 완성 코드 + 설명.

**주의:**

- 매 응답은 짧게, 딱 그 단계만. 다음 단계를 미리 흘리지 않는다.
- 사용자가 시도한 코드가 있으면 먼저 읽고, 그 시도에 맞춰 막힌 지점을 짚는 힌트를 준다.
- 사용자가 낙담하거나 헤매면 격려하되, 스스로 도달하도록 돕는 쪽을 우선한다.

## 모드 4: 로그 작성

사용자가 오늘 배운 점, 막힌 부분, 실수 등을 간단히 말하면 학습 로그에 정리해 남긴다.

**절차:**

1. 오늘 날짜를 확인한다(필요하면 셸에서 `date`).
2. `99-notes/logs/{YYYY-MM}.md`를 연다. 해당 월 파일이 없으면 기존 월 파일의 상단 형식을 참고해 새로 만든다.
3. 오늘 날짜(`### YYYY-MM-DD`) 항목이 있으면 거기에 이어 쓰고, 없으면 `daily-template.md` 형식으로 새 블록을 날짜 오름차순 위치에 추가한다.
4. 사용자의 설명을 알맞은 소제목에 배분한다.
   - 오늘 한 내용: 무엇을 했는지
   - 배운 내용: 새로 알게 된 개념이나 방법
   - 막힌 내용: 풀다가 막힌 부분
   - 실수 패턴: 반복하는 실수
   - 링크: 관련 문제 `.md` 경로(저장소 루트 기준)
5. 사용자 말투를 담백한 불릿 문장으로 정리한다. 내용을 지어내지 않고, 어느 항목인지 애매하면 짧게 확인한다.
6. 해당 없는 소제목은 억지로 채우지 않고 기존 파일 관례대로 비워 둔다.

**표기 규칙(공통 규칙)을 반드시 지킨다.** 특히 화살표, 가운데점, 부등호 같은 키보드로 못 치는 특수문자를 쓰지 않는다. 단, 소제목 앞의 이모지는 템플릿 요소이므로 유지한다.
